系统把「检测盒」作为核心商品，用三条主线把分散的角色串起来：订单流管钱和货，样本流管检测履约，权益流管客户归属与分佣。归属不看谁先点链接，看客户手里那盒检测盒上的码：出库时码已绑定出货渠道，客户扫码激活即归属该渠道，同时这份样本也有了唯一身份。报告内容按归属对渠道方开放，C 端可关闭授权并自查浏览记录。分销做两级，一级是归属渠道、二级是其邀请上级。商家在 B 端小程序用预付款采购、查看本店渠道的客户报告；系统只记账不碰钱，金额在后台算清、按周期出对账单。报告与解读完成后通知商家，由商家转给客户；对外怎么讲，由平台统一课程与合规素材约束。

00关键决策

以下七条是本方案的地基，任何一条被推翻都会改变功能结构和开发量，建议评审时优先对齐。

D1

系统只记账，不碰资金

不代收货款、不做自动分账、不做提现打款。金额在后台算清并按周期出对账单，资金收付与开票在线下完成。好处是不涉及支付与税务资质，上线快；代价是账实一致依赖线下对账纪律，系统只能保证算得准、记得清。

D2

分销做两级，层级硬上限

一级是订单归属人，二级是其邀请上级。系统在数据结构上把深度限制为 2，第三级无法创建，不靠配置约束。二级佣金只按商品成交金额计算，不按发展人员数量计酬。

D3

盒码即渠道，扫码即归属

每盒检测盒出库时生成唯一盒码，并绑定出货渠道。客户扫码激活的同时完成两件事：这份样本是谁的，这一单算哪个渠道。归属一次写定，不设保护期，不做点击归因，争议以盒码为准。

D4

报告内容对渠道方可见，以订单归属为界

商家、合伙人、销售可查看自己所辖订单的报告、解读与营养方案，用于向客户解释和服务。C 端在下单与激活时被告知，可随时关闭授权；每次查看留痕，C 端可自查浏览记录。跨归属不可见。

D5

未取得票证不算结清

对账单逐户显示应付金额与已登记票证金额。没有发票或收据的部分保持「未结清」，不因线下口头确认就标记完成。这样「开不了票」在系统里是一个看得见的口径，而不是账算完才发现付不出去。

D6

培训只做记录，不设交易门槛

课程由平台统一提供，销售与合伙人自主完成。完成情况与考试成绩作为能力与合规留痕，供平台和商家查看，但不阻断上架、下单或出库。是否对未完成培训的人采取措施，由商家自行管理。

D7

报告通知商家，由商家转给客户

报告与 AI 解读完成后，系统在后台通知平台，并通过微信服务通知提醒商家小程序；商家查看后一键转发给对应消费者。推送只带「报告已生成」与入口，不携带指标数值；入口需身份校验，转发出去的卡片对第三人无效。

01背景与目标

一条完整的检测生意链上同时存在多种角色：上游供应商与实验室提供检测盒和报告，平台提供商城与账目，下游商家、合伙人、销售负责获客和服务，C 端用户完成购买与采样。链条一旦跨过三个角色，五类问题会同时出现：

  • 归属问题。同一客户可能被多个渠道接触，靠聊天记录和表格争不出结论；销售离职时客户能不能带走，也没有规则。
  • 算账问题。两级分销之后，一级与二级的比例、退款冲回、层级变更叠加在一起，靠表格算不清，合伙人也无法核对每笔佣金的来源。
  • 凭证问题。合伙人多为自然人，无法开具发票；线下对账缺少统一的应付口径与票证登记，平台与合伙人双方都承担税务风险。
  • 交付问题。报告和解读分散在微信与邮件里，渠道方要反复截图转发，既低效也无法保证口径一致；谁看过、谁改过，事后无法还原。
  • 说错话的问题。真正面对客户的是销售和合伙人，他们若承诺疗效、解读超出边界，风险由平台承担，而平台没有培训与授权的抓手。

产品的回应是把这些问题各自收敛到一个机制上：盒码固定归属、下单快照固定算账口径、对账单与票证登记固定结清口径、报告按归属开放并留痕、培训考核固定对外表达资格。

目标（以可观察的结果描述）

  • 任意一笔 C 端订单，都能由盒码追溯到唯一归属渠道、唯一归属销售、唯一样本与唯一报告版本。
  • 合伙人可在系统内逐单看到佣金的计算基数、比例、层级、金额、规则版本与当前对账状态。
  • 每个结算周期，供应商、商家、合伙人各拿到一份可逐单下钻的对账单，数字与后台总览一致。
  • 对账单上能直接看出「已登记票证」与「未取得票证」的金额，未取得票证的部分不会被标记为结清。
  • 渠道方可在自己的订单范围内直接查看报告与解读，不需要线下索要；C 端能看到谁在何时看过自己的报告。
  • 商家能在 B 端小程序用预付款完成进货，并在同一处看到本店渠道消费者的报告与 AI 解读。
  • 报告与解读完成后提醒商家转发，通知与转发记录均可追溯。
  • 培训完成情况与考试成绩可追溯，作为平台与商家管理对外表达口径的依据。
  • 商家与销售无需自行设计物料，即可生成带自己渠道码的推广素材与服务话术。

2.3 盒码：一个二维码，两个答案

平台不再靠「谁先点链接」判断客户归谁，而是靠一个物理凭据：检测盒上贴的那张码。它在出库时生成，已经绑定了出货渠道。客户扫码激活时，同一次操作回答两个问题——这份样本是谁的，这一单算哪个渠道。

权益扫一次即定渠道

  • 码在出库时绑定出货渠道（商家 / 合伙人 / 平台自营）
  • 客户首次激活即归属该渠道，不需要再扫码抢客
  • 归属一次写定，不可转移；之后再扫只更新样本状态
  • 不设保护期，也不存在「首次点击」或「最后点击」归因

履约一盒一码一身份

  • 码值全局唯一，一盒一个，不可复用
  • 绑定出货渠道、采购单、批次与激活人实名
  • 退款或作废后码失效，不能再被激活
  • 报告只认这个码对应的实名，不认转发的链接

物理上可以是一张合成码（扫码同时解析渠道与盒号），也可以是「渠道码 + 盒号」两张标。系统按合成码设计；若实际使用两张标，以盒号为准绑定归属。

2.4 两个商城不能混

商家进货与消费者购买是两条链路，商品池、价格、结算方式、是否计佣都不同。系统里必须拆成两个入口，否则预付款扣错、佣金算错。

B 端采购商城

  • 使用者：商家（小程序）
  • 买什么：检测盒、耗材、采样包
  • 价格：供货价 / 平台采购价
  • 怎么付：预付款余额扣减，线下充值入账
  • 产生：采购单，不产生分销佣金
  • 票证：平台对商家开票，线下完成

C 端零售商城

  • 使用者：消费者（C 端小程序 / H5）
  • 买什么：检测盒 + 报告解读服务
  • 价格：零售价，不得低于平台底价
  • 怎么付：商家线下收款或既有收款方式，系统登记状态
  • 产生：销售单，按盒码归属算两级佣金
  • 履约：盒码 → 实验室 → 报告与解读 → 微信送达

03范围与边界

3.1 一期 P0（最小完整闭环）

四个闭环必须同时成立，缺一个都不算「跑通」：交易闭环、履约闭环、结算闭环、合规底座。

闭环包含能力完成标志
P0-A 交易 B 端小程序、采购商城、预付款账户、商品与批次、采购单、销售单、账目记录 商家能在小程序用预付款完成一次采购，C 端能完成一笔下单
P0-B 履约 商家入驻生成渠道身份、采购出库生成并贴附盒码、扫码归属、样本激活与收样、报告发布、AI 解读与营养方案、微信送达 一盒检测盒从出库贴码到报告送达消费者全程有状态，归属在扫码时一次写定
P0-C 结算 两级佣金计算、账目账本、对账单、票证登记与结清 合伙人能在对账单上逐单核对一级与二级佣金，差异有处理记录
P0-D 合规与能力 实名与资质、电子合同（商家与供应商）、线下协议登记、销售培训与学习记录、留痕查询、素材模板、商家与销售工作台 未完成电子签的商家不能上架、供应商不能供货；任一订单可导出完整证据链

3.2 P1（一期不做，但结构上预留）

  • 商家自有 App 或官网通过开放接口接入 AI 解读能力。
  • 销售提成：商家自设比例，从商家收入中扣减后发放给销售。
  • 阶梯佣金、季度激励、区域保护等激励规则。
  • 营养师排班、服务工单、付费增值服务包。
  • 培训相关：直播授课、AI 陪练对练、积分与排行榜、电子证书。
  • 合同相关：批量签署、合同模板可视化配置、第三方存证区块链对接。
  • 优惠券、拼团、直播分销等营销玩法。
  • 供应商自动对账与税务服务商直连开票。

3.3 明确不做

以下五条不是排期问题，而是产品边界，写在这里是为了避免后续需求反复：

  • 不做三级及以上分销，不做按发展人员数量计酬的团队奖励。
  • 不做基于点击、加好友或聊天记录的归属判定，归属只认盒码。
  • 不在报告或解读中输出疾病诊断、处方药推荐与疗效承诺。
  • 不向渠道方提供报告内容的二次编辑、改写或自制「解读版」，渠道方只能引用系统内的报告与解读，保证对 C 端的口径唯一。
  • 不做在线资金清结算：不代收货款、不做自动分账、不做提现打款、不代扣代缴。资金与发票均在线下完成，系统只负责计算、记账与对账。
关于「参考」部分的说明：需求原文中的「参考 / 实验室 生产生成报告」指向实验室侧的报告生成能力。本期只定义报告在系统中的接收、审核、发布与版本管理；是否需要直连特定实验室的 LIS 或检测仪器接口，属于集成范围，需在 Q10 确认后再决定是否纳入一期。

4.1 一次完整的成交（主路径）

  1. 供应商建品并报供货价，平台审核上架，设定零售价、平台服务费率与两级佣金比例，并为该商品配置建议学习的课程。
  2. 商家入驻审核通过，系统生成该商家的渠道身份码，并由平台开放其可售商品范围。
  3. 商家在小程序采购商城选品，用预付款余额下单，平台按采购单发货。
  4. 出库时为每一盒生成唯一盒码，并把该商家的渠道身份写入盒码，贴附在包装上发出。
  5. 商家把检测盒交付给客户并登记成交金额（线下收款或既有收款方式，系统不代收）。
  6. 客户扫码激活：完成实名、填写采样问卷、签署服务协议与知情同意书。激活的同一刻，客户归属到盒码所绑定的商家，样本也获得唯一身份。
  7. 客户采样并寄回，实验室收样、检测、出报告，审核发布。
  8. 报告发布触发 AI 解读；若用户购买了营养师服务，营养师复核并出具营养方案。渠道方在同一时刻可查看本店归属的报告。
  9. 解读完成后系统通过微信服务通知把报告送达消费者，商家也可在小程序内一键转发；送达与查看均留痕。
  10. 报告交付完成，售后期满后一级与二级佣金转入待对账；系统按周期生成对账单，财务线下核对并登记票证，标记结清。

线上直接下单是另一条入口：出库时按订单预归属渠道生成盒码，客户激活后以盒码为准；若实际使用的盒子来自其他渠道，归属随之改写并留痕。

4.2 关键失败路径必须先定义

  • 样本不合格：实验室登记异常原因，系统按原归属渠道生成新盒码并补寄，不向 C 端重复收费。
  • 订单退款：按 SKU 实付比例冲回账目与两级佣金；若已结清，在下一期账单生成负数调整行。
  • 归属争议：以盒码为准，平台只处理盒码异常（标签破损、发错货、系统错绑），不处理「谁先联系客户」这类主张。
  • 对账差异：主体不认可账单时，账单停在「差异处理中」，差异需录入原因并有人确认，不影响其他主体的对账进度。

05功能需求

共 16 个功能域，每个需求按「目的 → 触发 → 规则 → 异常」组织。规则部分是可以直接进入开发判断的行为描述，不是目标描述。

FR-01账号、组织与实名

目的建立多角色身份与组织归属，让后续的权限、归属、结算都有明确主体。

触发平台创建账号，或角色自助注册后由平台审核。

规则
  1. 平台可创建供应商、实验室、商家、合伙人、营养师账号；商家可创建本店销售账号，销售不可跨商家存在。商家审核通过时生成唯一的渠道身份码。
  2. 同一主体可同时拥有商家与合伙人身份，但同一笔 C 端订单只按盒码判定一个归属，不叠加佣金。合伙人可绑定一个邀请上级，形成两级渠道关系，深度由系统硬限制为 2。
  3. 商家须提交营业执照与法人身份证；供应商须提交营业执照与生产或经营许可；合伙人须提交身份证与已签协议；营养师须提交相关职业资质。资质信息由各身份用户在后台自行维护与补充，平台审核；到期前 30 天提醒更新。
  4. C 端用手机号注册。购买检测类商品必须完成实名，并按检测项目采集必需信息（性别、年龄、采样条件等），字段随项目配置，不硬编码。
  5. 账号停用不删除历史数据；停用后其渠道身份与未激活盒码立即失效，未对账佣金进入人工处理队列。

异常资质过期 → 限制新订单与推广并提示更新；同一主体重复注册 → 由平台判定合并或拒绝，合并需保留原归属关系。

FR-02商品、供货价与批次

目的把检测盒做成可定价、可分销、可履约的标准商品，而不是一个只有名字和价格的 SKU。

规则
  1. 供应商维护 SKU：名称、检测项目、样本类型、采样方式、保存条件、有效期、供货价、建议零售价、是否允许分销。
  2. 平台审核上架，并设定零售价、平台服务费率、佣金比例上限、可售渠道范围，并为该商品配置建议学习的课程（不影响可售）。
  3. 商家从平台可分销商品池选品上架，售价不得低于平台底价，加价部分归商家。
  4. 批次：供应商按批入库，记录批次号、生产日期、有效期、数量；发货按先进先出，过期批次不可出库。
  5. 盒码：出库时为每一盒生成唯一盒码，写入出货渠道、批次与采购单；贴标在出库环节完成，漏贴或破损按补码流程处理。
  6. 库存扣减以支付成功为准；未支付订单不占用库存，下单时校验库存，支付成功才扣减。

异常库存不足 → 阻断下单并提示可替代商品；在途批次临期 → 拦截发货并通知供应商换批；商品下架 → 已在途订单继续履约。

FR-03盒码、渠道归属与客户绑定

目的让客户归属有一个不可争辩的物理凭据，而不是靠谁先加微信、谁先发链接。归属的确认点只有一个：客户扫码激活的那一刻。

规则
  1. 商家入驻审核通过后，系统生成唯一的渠道身份码，用于线上推广、素材嵌入与结算主体识别。
  2. 商家在 B 端商城完成采购、平台出库时，按采购数量为每一盒生成唯一盒码，写入出货渠道、批次与采购单。贴标默认由平台在出库环节完成；若改为商家自行贴标，需提供批量打印与绑定工具 Q17。
  3. 客户扫码 → 系统解析盒码 → 首次激活即把该客户归属到盒码绑定的渠道，同时建立样本。归属与样本在同一次操作中完成，不可拆分。
  4. 归属长期有效，一次写定，不设到期；不采用「首次点击」或「最后点击」归因。已归属客户再扫其他渠道码，只记录触点，不改变归属。
  5. 线上直接下单的场景：出库时按订单预归属渠道生成盒码；若客户实际使用的是另一渠道给他的盒子，以盒码为准，预归属在激活时被改写并留痕。
  6. 换绑仅平台可执行，且只处理盒码异常（发错货、标签错贴、系统错绑）；已激活的归属不变。记录原因、操作人与变更前后值。
  7. 销售归属：盒码只确定商家或合伙人层级。销售归属由商家在后台或小程序分配，或客户激活时扫描销售推荐码确定，以先发生为准，不改变一级渠道归属。
  8. C 端在「我的 - 归属」可查看归属商家与对接销售。

异常同一盒码被两人扫描 → 首人激活成功，第二人提示「该盒已被使用」并转客服；客户拿错盒（盒码与订单不符）→ 以盒码实际绑定的渠道为准，同时提示可能拿错，平台可介入；盒码未激活即退款 → 码作废；标签破损无法识别 → 客服按采购单与批次补发盒码，原码作废；销售离职 → 客户归属在商家，不随销售离职转移，只调整销售分配关系。

FR-04订单流（采购单与销售单）

目的用两种订单分别承载「进货」和「零售」，让金额、库存、履约各自可核对，不混在一张单子里。

A. 采购单（商家 → 平台 / 供应商）
  1. 商家在 B 端小程序采购商城按供货价下单，默认从预付款余额扣减；账期采购一期不做。
  2. 余额不足时阻断提交，显示差额与充值指引；余额充足时提交即冻结对应金额。
  3. 冻结后锁定批次库存，供应商发货，商家确认收货后冻结金额转为实际扣减。
  4. 状态：已扣款 → 待发货 → 已发货 → 已收货 → 已完成；旁支：已取消（余额退回）、售后中、已退款（退回余额）。
B. 销售单（C 端 → 商家店铺）
  1. C 端可经有效渠道码进入线上商城，该渠道记为预归属渠道；也可从平台商城直营入口进入并归属平台自营。
  2. 系统不做代收，支付状态由商家或财务登记；订单金额按 FR-09 的规则生成账目。
  3. 下单快照：固化商品价、供货价、平台服务费率、佣金比例、预归属渠道与规则版本。预归属仅用于出库生成盒码；最终归属以客户扫码激活的盒码为准，二者不一致时按 FR-03 改写并留痕。
  4. 一单多 SKU 时，按 SKU 分别计算佣金与账目，不做整单均摊。
  5. 退款支持整单与部分退款，账目与佣金按 SKU 实付比例冲回。
  6. 状态：待支付 → 已支付 → 待发货 → 已发货 → 待采样 → 检测中 → 报告已出 → 已完成；旁支：已取消、退款中、已退款、售后中。
  7. 待支付订单 30 分钟未支付自动关闭。

异常支付成功但批次库存失效 → 自动退款并通知，不允许人工改成缺货发货；报告长期未出 → 订单不自动完成，进入异常看板由平台跟进；重复支付回调 → 幂等处理只生成一笔订单。

FR-05样本激活、收样与检测

目的让「一盒检测盒」对应「一份可追溯的样本」，避免报告挂错人、样本来源说不清。

规则
  1. 出库时按采购数量生成盒码，唯一且一次性使用，印刷或贴附于采样盒，同时写入出货渠道。
  2. C 端扫码激活：校验盒码状态与实名 → 填写采样问卷（必填项由检测项目配置）→ 签署检测服务协议与知情同意书 → 选择上门采样或自行采样寄回。激活成功的同一刻写入客户归属。
  3. 知情同意书需同时确认报告可见范围：报告内容将向所属渠道方开放，用于解读与随访；C 端可随时关闭该授权。
  4. 盒码激活后不可转移到其他用户；未激活的盒码在订单退款或采购退货时作废。
  5. 样本状态：已生成 → 已激活 → 待寄出 → 运输中 → 实验室已收样 → 检测中 → 报告生成 → 已发布；旁支：样本异常、样本作废。
  6. 实验室收样需核对盒码、采样时间、保存条件与运输时长；不合格时登记异常原因并触发补采。
  7. 补采：系统按原归属渠道生成新盒码并安排补寄，补采上限 2 次，不向 C 端重复收费。

异常盒码被重复扫码 → 第二人不可激活，提示联系客服；样本超期送达 → 实验室可拒收并触发补采；报告需更正 → 生成新版本，旧版本归档，通知 C 端并留痕。

FR-06报告发布与按归属可见

目的报告既是检测业务的核心资产，也是渠道方服务客户的主要抓手。可见性要同时满足两件事：渠道方讲得清，平台说得清谁看过。

规则
  1. 实验室完成检测后在系统内生成报告，经审核后发布；发布前 C 端只看到「检测中」，看不到任何中间结果。
  2. 可见范围以订单归属为边界：
    • C 端：本人报告、本人解读、本人方案。
    • 销售：本人负责客户的报告、解读与方案。
    • 商家：本店订单对应的报告、解读与方案。
    • 合伙人：本渠道订单对应的报告、解读与方案。
    • 营养师：被指派且 C 端已授权的报告。
    • 实验室：样本与自己出具的报告。
    • 平台：全量。
  3. 授权与撤回：C 端在激活样本的知情同意中被告知「报告内容将向所属渠道方开放」；C 端可在隐私设置中关闭。关闭后渠道方仅见「报告已出 / 解读完成」状态，不见内容，此前的查看记录仍保留。
  4. 查看留痕：渠道方每次查看报告，记录查看人、角色、时间、报告版本与来源设备；C 端可在「我的报告 - 查看记录」看到谁在何时看过。
  5. 内容一致：渠道方看到的与 C 端是同一份报告与同一版解读，不做删减版、不做渠道专供版，避免口径分叉。
  6. 页面防护：报告页展示动态水印（查看人 + 时间），降低截图外传风险；允许下载，下载行为记录到留痕；转发卡片仍需身份校验。
  7. 报告页面固定展示「本报告仅用于健康风险提示，不作为临床诊断依据」，位置与文案由平台锁定，不可被商家覆盖。

异常发布失败 → 保留草稿并告警，C 端状态不前进；C 端撤回授权时渠道方正在查看 → 会话立即失效并记录；报告指标缺失 → 允许发布部分项目并标注缺项；渠道方越权访问非本归属报告 → 拒绝并记录尝试。

FR-07AI 报告解读与营养方案（解读端口）

目的把报告翻译成 C 端看得懂的行动建议，并让营养师在 AI 结果上做人工增值。这是渠道方愿意卖检测盒的核心服务能力，也是渠道方讲解时的统一口径。

规则
  1. 触发：报告发布后自动发起解读任务；营养师也可手动重跑。
  2. 输入：结构化报告指标、采样问卷、C 端基础信息。不引入未授权的历史数据与其他客户的相似数据。
  3. 输出结构固定为六段：指标释义、异常项说明、可能影响因素、饮食与生活方式建议、复检建议、免责声明。
  4. 内容边界：不输出疾病诊断，不推荐处方药与剂量，不做疗效承诺与治愈率暗示；命中敏感表述时拦截并要求人工复核，词表由平台运营维护，首版包含诊断、治愈、疗效、处方药、替代药物等。
  5. 展示：C 端只读；渠道方在其订单归属范围内只读，与 C 端看到的版本完全一致；营养师可编辑。标注「AI 生成」、生成时间、模型版本；营养师复核后展示复核版本，并标注「已由营养师复核」及复核人。
  6. 营养师操作：采纳、编辑、加注、驳回重生成；可基于模板产出营养方案（周期、餐次建议、随访节点）。
  7. 端口：C 端 H5 / 小程序只读端口；B 端营养师工作台；渠道方从订单详情进入同一份解读，不另开一套内容。送达规则见 FR-16。
  8. 留痕：保存 AI 原始输出、提示词版本、模型版本、复核前后差异、发布人与时间，进入 FR-14 的留痕中心。

异常AI 服务不可用 → 报告照常发布，解读区显示「生成中 / 暂不可用」并支持重试，不阻塞 C 端看报告；复核超时 → 不自动发布未复核版本，提醒平台人工处理；用户撤回授权 → 已发布内容保留但停止后续更新，渠道方同步失去访问权。

FR-08素材与模板中心

目的让商家和销售不用自己做物料就能服务散户，同时保证对外口径与合规文案统一。

规则
  1. 平台素材库：海报、详情图文、朋友圈文案、短视频脚本、检测项目说明、常见问题、合规话术。
  2. 商家基于模板生成自有素材：自动嵌入商家名称、门店信息与本人渠道码二维码，生成结果即时预览、可下载。
  3. 服务模板：报告解读话术、营养方案框架、随访提醒、复检提醒，供商家与营养师取用。
  4. 平台锁定项（资质说明、免责声明、检测范围、价格口径）不可编辑、不可删除，只能整体使用。
  5. 素材可设有效期与适用商品范围；下架后不可再生成，已分发的不追溯。
  6. 使用记录：谁在何时生成了哪一版素材、用了哪个渠道码，均写入留痕。

异常模板含违规词 → 生成时拦截并指出具体位置；渠道码已失效 → 生成时自动替换为新码并提示；素材涉及未上架商品 → 不可生成。

FR-09两级分销佣金计算

目的把每一单该算给谁、按哪一级算、算多少算清楚。系统只出数字、不处理资金，但数字必须能逐单下钻，经得起线下对账。

层级结构
邀请上级（二级）→ 订单归属人（一级）→ C 端订单

箭头方向即分佣方向：订单归一级，一级的邀请人拿二级。系统把深度硬限制为 2，第三级在数据结构上无法创建。

规则
  1. 层级上限：每个合伙人可绑定一个邀请上级，形成且仅形成两级。禁止自邀、禁止循环邀请、禁止跨级绑定。
  2. 计佣对象：一级 = 客户激活盒码所绑定的渠道；二级 = 该渠道的邀请上级。无上级时只计一级。
  3. 防重复计酬：同一主体在同一订单上只能取得一种收益。商家取得商品差价，不再取得二级佣金；销售提成由商家自行发放（P1），不参与分销层级。
  4. 比例配置：按 SKU × 层级 × 生效时间配置，支持固定比例与固定金额。一级与二级比例之和不得超过平台设定的佣金上限，保存时即校验。
  5. 计算基数 = 商品实付金额 − 运费 − 平台优惠分摊 − 退款金额。按已确认口径实现，字段结构保留毛利口径的扩展位，便于后续切换。
  6. 账目构成：商品实付 = 供应商货款 + 平台服务费 + 一级佣金 + 二级佣金 + 商家收入。尾差计入商家收入。
  7. 快照：下单时固化一级与二级的归属主体、层级关系、比例与规则版本；之后调整关系或比例不影响已支付订单。
  8. 归属口径：佣金归以客户激活的盒码确定的渠道为准。下单时的预归属只用于出库，若与盒码不一致，按盒码改写归属，原预归属对应的佣金作废重算。
  9. 幂等：同一订单、同一层级、同一规则版本只生成一条佣金流水，重复回调不重复计佣。
  10. 自购不返：一级或二级与下单人实名一致时，该层佣金不生效，记录保留但不进入对账单。
  11. 退款：按 SKU 实付比例同时冲回一级与二级，累计冲回不超过该层原佣金金额。

异常上级账号停用 → 二级佣金照常计算但标注「归属待确认」，由平台在对账前裁定；层级关系变更 → 需平台审批，变更只对新订单生效；比例之和超上限 → 保存失败并提示超出的层级；规则缺失 → 订单仍可成交，佣金进入「待定」并告警。

FR-10对账、票证登记与结清

目的直接对应「所有的账只在后台显示数字，线下会进行对账」与「合伙人分佣担心开不了票」。系统不做资金清结算，只负责把数字算准、把对账单出对、把票证与结清状态记清。

系统不做的事
  • 不代收货款、不做自动分账、不做提现与打款、不代扣代缴。
  • 不判断税务处理方式，不给税务结论；票种、税率与开票主体由线下决定。
  • 资金收付、发票开具与流转全部在线下完成，系统只登记结果。
规则
  1. 对账单生成：按周期（默认自然月）× 主体（供应商 / 商家 / 合伙人）生成。内容包含上期未结清、本期新增应付、退款冲回、调整项、本期应付合计、已登记票证金额、未取得票证金额。
  2. 逐单下钻：对账单每一行对应一个订单或一条佣金流水，显示基数、比例、层级、金额与规则版本。
  3. 对账状态：待对账 → 对账中 → 已对账 → 已结清；旁支：有差异 → 差异处理中 → 已对账。
  4. 差异处理：线下核对后由财务录入差异金额、原因与处理方式（调整账单 / 补开票 / 下期抵扣），差异必须有人确认并留下记录。
  5. 票证登记：财务按账单登记发票或收据的号码、抬头、金额、开具日期与影像件；系统校验金额与账单应付是否一致，不一致转入差异。
  6. 结清条件：只有「已对账」且「已登记票证金额覆盖应付金额」的账单才可标记已结清。未取得票证的部分保持未结清，并在总览中单独显示。
  7. 后台总览：显示应付总额、待对账金额、未取得票证金额、差异金额；任一数字可下钻到订单与佣金流水。
  8. 导出：对账单支持 Excel 与 PDF 导出，字段与现行线下对账表一致，含订单号、商品、实付、各项金额、退款与应付合计。
  9. 留痕：对账、差异处理、票证登记、结清与反结清，全部记录操作人、时间、前后值。
边界声明：系统不承担税务处理，也不在界面里给出税务结论。票种、税率、代征或自开的选择属于线下与法务财务的决策；系统只保证「应付多少、已收到什么凭证、还差多少」这三件事在后台说得清。

异常账单生成后发生退款 → 生成调整行，不修改原账单；票证金额不足 → 差额保留未结清；同一发票重复登记 → 校验拦截；已结清后发现错误 → 反结清需审批，并生成调整账单；主体不认可对账结果 → 账单停在「差异处理中」，不影响其他主体的进度。

FR-11合同签署与协议登记

目的把佣金比例、开票义务、报告使用范围、禁止性条款这些有法律后果的约定固化。电子签只覆盖商家与供应商两类合同，其余走线下签署加后台登记，避免为少量合同引入完整电子签改造。

合同类型与签署方式
合同签署方关键条款签署方式时点
入驻与供货合作协议平台 + 商家供货价、零售底价、售后责任、报告使用范围电子签首次上架前
供货协议平台 + 供应商质量标准、批次与有效期、缺货与召回责任电子签首次供货前
分销合作协议平台 + 合伙人佣金比例与结算周期、开票义务、报告使用范围、禁止性条款线下签署 + 后台登记首次对账前
服务合作协议平台 + 营养师服务范围、解读边界、保密与授权线下签署 + 后台登记首次接单前

规则
  1. 电子签范围：仅平台与商家、平台与供应商两类合同。电子签通过统一适配层同时接入 e签宝与腾讯电子签，可在后台切换服务商；切换只影响新发起的签署任务，已签合同与存证不受影响。
  2. 电子签流程：平台发起 → 生成待签文件 → 签署方实名核身 → 签署 → 平台盖章 → 归档生效。
  3. 线下协议：合伙人与营养师协议在线下签署，后台登记合同编号、签署日期、有效期、扫描件与登记人。
  4. 线上同意：C 端在激活盒码时勾选检测服务协议与知情同意书，系统记录模板版本、确认时间、IP 与设备，不做电子签名。
  5. 模板版本化：模板有版本号；已生效的合同不可修改；条款变更生成新版本，电子签触发重签，线下协议重新登记。
  6. 未签拦截：电子签未完成时阻断商家上架与供应商供货；合伙人协议未登记时账单照常生成，但结清按钮提示「协议未登记」，需平台确认后放行。
  7. 佣金条款与系统规则的关系：系统内佣金比例调整只对新订单生效，不自动变更已签合同；合同约定固定比例的，变更需签补充协议。
  8. 续签与终止：到期前 30 天提醒；终止后渠道身份失效，未对账佣金按合同约定处理。
  9. 存证与台账：电子签保存文件哈希与存证编号；线下协议保存扫描件与登记信息；按主体可查全部合同、生效版本与到期日。

异常电子签服务商不可用 → 流程顺延，商家上架与供应商供货保持阻断；线下协议扫描件缺失 → 台账标红并提醒补录，不阻断交易；C 端未勾选同意 → 无法激活盒码；主体信息变更 → 触发重签或重新登记。

FR-13商家小程序与销售工作台

目的让商家在手机上就能进货、看客户、看报告；让销售在自己的数据边界内看清客户、算清收入、拿到素材。这也是需求中「自己的销售看到自己负责的客户、客单价、绑定客户」的落地位置。

商家小程序（B 端）
  1. 首页：商家名称与资质状态、可用预付款余额、待办（待充值、待对账、待签合同、待学课程）。
  2. 采购商城：平台可采商品、供货价、起订量、库存；下单扣减预付款。
  3. 预付款：可用余额、冻结金额、充值记录、扣减流水，可导出。
  4. 我的客户：通过本商家盒码激活的消费者列表，含归属销售、成交金额与报告状态。
  5. 报告与解读：本店渠道消费者的报告可直接查看，AI 解读同屏展示；可一键转发给消费者。
  6. 我的生意：订单、收入、佣金支出、月度对账单入口。
  7. 素材与培训：素材生成、课程与考试入口。

  1. 选品上架、定价（不低于平台底价）、库存查看。
  2. 订单履约：发货、填写物流、处理售后。
  3. 客户与销售管理：创建销售、分配客户、查看客户归属与成交情况。
  4. 报告与解读：本店订单对应的报告可直接查看；可查看哪些销售看过哪份报告。
  5. 培训管理：本店销售的学习进度、考试结果、授权到期名单。
  6. 收入账单与佣金支出明细，可下钻到订单。

  1. 我的客户：客户列表、归属时间、累计成交单数、累计成交金额、客单价、最近下单时间、报告状态。

FR-14合规留痕与查询

目的需求原文提到「体系合规服务客户，主要是记录：1、订单流 2、AI 智能报告解读端口」。这一条落地为独立的留痕中心，承载全链路证据，而不只是订单日志。

规则
  1. 留痕对象：合同签署与终止、C 端授权与撤回、订单流（下单 / 支付状态登记 / 发货 / 退款）、盒码生成与归属变更、样本流转、报告版本、报告查看记录、AI 解读版本、营养师操作、两级佣金计算、对账与票证登记、培训学习与考试成绩、授权授予与撤销、素材生成。
  2. 每条记录包含：业务单号、操作类型、操作人、角色、时间、来源 IP 或设备、变更前后值、关联凭证。
  3. 只追加不修改：留痕记录不可编辑与删除，更正以新增记录表达，保留原始记录。
  4. 查询：按订单号、盒码、客户、渠道、合伙人、时间区间检索；平台合规角色可查全量，其他角色仅见与自己相关的记录。
  5. 导出：支持按客户或按订单导出全链路凭证包，格式为 PDF 汇总加 Excel 明细。
  6. 留存期限：报告与解读相关记录留存 1 年；合同、佣金与对账记录按财务档案要求留存 10 年；到期销毁需审批并留痕。

异常记录缺失 → 系统巡检发现断点并告警，不允许静默跳过；越权查询 → 拒绝并记录尝试行为；导出含敏感信息 → 需二次确认并记录导出人与用途。

FR-15预付款账户与充值入账

目的商家先充值、再采购，采购不依赖线上支付。系统不碰资金，预付款只是一个受控的余额台账，但它必须对得上账、追得到凭证。

账户结构
字段含义计算关系
可用余额当前可直接用于下单的金额累计充值 − 累计扣减 − 冻结金额
冻结金额已下单未收货的占用金额由采购单状态驱动
累计充值线下打款并入账的总额所有充值单之和
累计扣减已完成采购的实际扣款总额所有已完成采购单之和
规则
  1. 充值流程：商家线下打款 → 上传打款凭证 → 平台财务登记入账 → 可用余额增加。系统不发起支付、不对接银行。
  2. 入账校验：同一笔打款凭证不可重复入账；付款方名称、金额与商家主体不一致时转入人工核验，核验通过才入账。
  3. 下单扣减：提交采购单即冻结对应金额；确认收货后转为实际扣减；订单取消或退款则解冻回可用余额。
  4. 余额不足：阻断提交，显示差额与充值指引，不允许负余额。
  5. 流水完整性：每次充值、冻结、扣减、解冻、退款生成一条流水，含操作人、时间、关联单号与变更前后余额。
  6. 对账联动：预付款流水进入 FR-10 的对账单，作为商家侧的付款依据。
  7. 权限：商家只能查看自己的账户与流水；平台财务可入账与调整，调整需审批并留痕。

异常打款金额与登记金额不符 → 差额挂账并由财务处理，不直接改余额；商家主体变更 → 余额迁移需审批；账户因违规被冻结 → 只可退款不可采购；余额与流水对不平 → 自动告警并锁定该账户的采购入口。

FR-16报告完成后的商家通知与转发

目的报告生成后如果没人告诉消费者，转化就断在最后一步。本版确认的送达路径是：平台后台可见，商家小程序收到提醒，由商家把报告转给客户；系统不直接向消费者推送。

规则
  1. 触发：报告发布且 AI 解读生成完成；含营养师复核的订单，在复核完成后触发。
  2. 平台侧：后台生成「报告待转发」待办，按商家归集；超过约定时长未转发，列表标红并提醒平台运营。
  3. 商家侧：通过微信小程序订阅消息提醒商家「有报告待转发」，附带脱敏订单信息；商家未订阅时用站内消息兜底。
  4. 转发：商家在小程序内选择报告卡片转发给消费者，可使用平台提供的话术模板，话术受 FR-08 的合规文案约束。
  5. 内容边界：通知与卡片只带「报告已生成」与查看入口，不含任何指标数值、异常项与结论。
  6. 入口校验：消费者点开需登录并校验手机号与订单归属，非本人不可打开；转发给第三人无效。
  7. 记录：记录通知对象、模板版本、发送时间与失败状态；记录转发人、时间与接收人。转发不改变报告归属与查看权限。
  8. 频率控制：同一报告对同一商家只自动提醒一次，商家可手动再提醒；报告更正后重新提醒一次并注明「报告已更新」。

异常商家未订阅消息 → 站内消息兜底并在后台标红；长时间未转发 → 同时提醒商家与平台运营；消费者未收到 → 商家可重新转发；报告更正后旧卡片被打开 → 提示查看最新版本并跳转；同一消费者有多笔订单 → 按订单分别通知与转发，不合并内容。

佣金

佣金有独立于订单的生命周期。订单完成不等于账能对清，中间隔着一个售后期与一次线下对账。

预估→ 待对账→ 对账中→ 已对账→ 已结清

合同

草稿→ 待签署→ 签署中→ 已生效→ 待续签→ 已终止

预付款

待入账→ 已入账→ 冻结→ 已扣减
已解冻← 订单取消 / 退款

余额与流水必须始终对平；对不平时锁定采购入口，先查账再放行。

6.3 金额与舍入

  • 所有金额以「分」为单位存储，展示保留两位小数，禁止用浮点数参与累计运算。
  • 计算顺序固定为：基数 → 比例 → 金额。舍入到分，四舍五入。
  • 多 SKU 账目拆分产生的尾差计入商家收入，不分摊到佣金，避免合伙人佣金出现零头争议。
  • 退款按 SKU 实付比例分摊，先冲佣金、再冲平台服务费、最后冲商家收入。
  • 快照优先：订单支付时固化价格、费率、佣金比例与规则版本；后续配置变更只对新订单生效。

6.4 风控与反作弊

  • 自购不返：一级或二级与下单人实名一致时，该层佣金不生效，记录保留但不计入对账单。
  • 层级异常：自邀、循环邀请、超深绑定、同一主体一日内频繁改绑上级，均阻断并告警；已生效的层级变更需平台审批。
  • 盒码异常：同一盒码短时间内被多个账号扫描、盒码在非出库渠道的订单上激活、补码后原码再次出现，均冻结该盒并转人工核查。
  • 异常注册：同设备、同 IP、同收款账户批量注册的账号进入风险名单，其订单佣金延迟进入待对账。
  • 高频退款：同一渠道月退款率超过 20% 时暂停该渠道账单进入对账并转人工审核。
  • 渠道码外泄：推广渠道码可一键停用并重新发码，已归属客户不受影响；已出库但未激活的盒码可批量冻结并补码，补码后旧码失效。
  • 预付款异常：同一打款凭证重复入账、余额短时大额跳变后集中下单、余额与流水对不平，均转人工并暂停采购入口。
  • 报告外传：报告页加水印并记录查看人，异常高频查看或跨归属访问触发告警；技术手段只能形成约束，不能完全阻止截图，需在合作协议中约定责任。
  • 培训作弊：异常答题速度、切屏超 3 次、同设备多账号考试触发标记，成绩作废并要求线下复核后重考。
