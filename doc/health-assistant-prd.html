移植后健康助手

产品开发文档（PRD + 技术方案） · 版本 v1.0 · 2026-10-27 · 状态：待评审
功能范围凡从商家处购买移植服务的 C 端消费者，接受移植服务后均可获得健康助手功能
核心行为依据服务流程文档中的注意事项，向消费者推送早、中、晚三个时段的通知；并在移植前提醒服用清肠药物（平台购买 / 用户自购两条路径）
技术栈落点apps/api（NestJS + Prisma + @nestjs/schedule）、apps/mini-c（Taro4 C 端）、apps/mini-b（Taro4 商家端）、apps/admin（React + antd5）、packages/shared
术语约定「移植日」= 用户开始服用胶囊的第一天，记为 D0；「旅程」= TransplantJourney，一次完整移植服务的健康管理周期

01背景与目标

平台已承接武汉百英诺生物的菌群移植业务：消费者从商家购买移植服务后，需经历 移植前 7 天准备 → 移植前 1 天清肠 → 6 天移植期 → 30 天恢复期 共约 43 天的完整周期。服务流程文档对每个阶段有明确的注意事项（用药禁忌、饮食禁忌、服药方法、不良反应处理），但目前这些要求仅以纸质/PDF 形式交付用户，执行情况完全依赖用户自觉，商家也无法感知用户是否按规程准备。

观察到的链路断点：

  • 移植前 1 天清肠是移植成败的关键前置步骤（聚乙二醇电解质散清洁肠道至无渣清水状），但药物需要用户提前备好——遗漏或临时买不到药会直接导致移植延期；
  • 移植期 6 天每天需按时、按法服用胶囊（晨起空腹、≤37℃ 温凉水送服、服后 1 小时禁食），规则细碎，纯靠记忆易出错；
  • 移植后 30 天内的饮食/运动/复检要求，以及腹泻、腹胀、轻度发热等自限性不良反应的应对，用户缺少即时可查的指导入口。

产品决策：为购买移植服务的 C 端消费者提供「健康助手」功能——以移植日为主线，按阶段自动生成早、中、晚三时段的推送计划，把文档中的注意事项转化为到点即达的执行指令；把清肠药物准备做成「平台购买 / 自行购买」双路径闭环，未就绪时升级提醒并同步商家跟进。

预期可观察结果：

  • 用户在每个阶段开始时即收到该阶段注意事项，不需要翻文档；
  • 清肠日前，清肠药物就绪状态可在系统内被确认（两条路径均可），未就绪时商家收到预警并可介入；
  • 商家可查看名下客户各自的旅程阶段与准备状态，平台可审计全部推送记录。

02目标用户与使用场景

2.1 角色定义

角色系统身份与本功能的关系
C 端消费者mini-c 用户（Role=customer）健康助手的唯一使用者：接收推送、设置移植日、确认清肠药物、查看今日任务
商家mini-b 用户（Role=merchant）移植服务的售出方：查看名下客户旅程、代设移植日、接收清肠未就绪预警并跟进
平台运营admin 用户（Role=platform）管理推送模板、查看全部旅程、手动补发/停用推送、处理异常
供应商Role=supplier仅作为清肠药物商品的供货方出现在购买链路中，不直接操作健康助手

2.2 典型场景

场景 A首次移植的完整周期

王女士在商家门店购买「精准菌群移植服务」，订单支付成功 → 健康助手自动开通，提示她设置移植日 → 设置后，移植前第 7 天起每天早中晚收到饮食与用药禁忌提醒 → 移植前 2 天收到「请确认清肠药物已备好」提醒，她选择从平台一键下单聚乙二醇电解质散 → 移植前 1 天晚饭后收到清肠操作指引（剂量、冲水量、服用方法）→ 移植期 6 天每天 07:30 收到服药提醒 → 移植后第 35 天收到宏基因组复检提醒，旅程结束。

场景 B自购清肠药

李先生是药店会员，收到清肠药就绪提醒后选择「我已自行购买」，填写药品名并确认 → 系统记录就绪，清肠日当天正常收到操作指引，商家端不再出现预警。

场景 C清肠药未就绪的商家介入

张先生直到移植前 1 天中午仍未确认清肠药 → 系统向他发送升级提醒（当日 12:00、19:30 各一次），同时向售出商家发送预警通知 → 商家电话联系后得知其已买到药，代为确认「已备好」，预警消除。

场景 D移植延期

陈女士移植前 3 天发热 37.8℃（文档禁忌：体温 ≥37℃ 不宜移植）→ 她在健康助手中暂停旅程并改期 → 未发送的推送任务按新移植日重建，已过的任务不重发。

3.2 健康助手生命周期

订单支付成功→ 自动开通（待排期）→ 设置移植日（激活）→ 准备期 D-7~D-1→ 清肠日 D-1 晚→ 移植期 D0~D5→ 恢复期 D6~D35→ 复检提醒后结束
开通时点的产品判断：需求描述为「接受移植服务后获得健康助手」，但清肠提醒发生在移植执行前 1 天，准备期注意事项从移植前 7 天即需执行。因此开通时点定为移植服务订单支付成功（而非移植执行完毕），支付后立即开通并进入「待排期」状态，设置移植日后才激活推送计划。这与「凡购买者均可获得」的授权语义一致，且覆盖了清肠提醒的时间窗。

3.3 主业务流程

  1. 触发开通（FR-HA-01）：订单含「移植服务」类商品且支付成功（订单状态进入 paid）→ 系统为每个移植服务商品行创建一条 TransplantJourney，状态 pending_schedule → C 端「我的服务」出现「健康助手」入口，并发送一条开通欢迎通知。
  2. 排期（FR-HA-02）：用户在健康助手页设置移植日（默认建议至少为 8 天后，保证完整准备期）与服药方案（首选：每日 1 次晨起空腹 10 粒；次选：每日 2 次、每次 5 粒，早空腹 + 晚饭后 1 小时）→ 系统生成全量推送任务 → 状态转 active。商家可代设。
  3. 阶段推进（FR-HA-03）：系统按「今天 − 移植日」的天数偏移 dayOffset 推导阶段：-7~-1 准备期（含 D-1 清肠）、0~5 移植期、6~35 恢复期、>35 自动完成。阶段不手工维护，由日期推导，避免状态漂移。
  4. 推送执行（FR-HA-04/05）：调度器每 5 分钟扫描到点任务，生成站内通知；内容按「阶段 × 时段 × 服药方案」从模板库取（见 4.3）。
  5. 清肠闭环（FR-HA-06/07/08）：D-2 起系统检查清肠药就绪状态；用户在健康助手中选择平台购买或自购确认；D-1 中午仍未就绪 → 升级提醒用户并预警商家。
  6. 结束：dayOffset > 35 且复检提醒已发送 → 状态转 completed，推送停止，历史可查。

3.4 旅程状态机

状态进入条件允许操作出口
pending_schedule 待排期订单支付成功自动创建设置移植日；取消（订单退款联动）→ active（设置移植日）；→ cancelled（退款）
active 进行中已设置移植日改期、暂停、恢复、清肠确认、接收推送→ paused；→ completed（dayOffset>35）；→ cancelled
paused 已暂停用户/商家暂停（发热、生理期、个人原因）恢复（必须重设移植日）；取消→ active（恢复并重建未发任务）；→ cancelled
completed 已完成dayOffset>35 且复检提醒已发仅查看历史终态
cancelled 已取消订单全额退款 / 平台取消仅查看终态
约束：同一用户同一时刻最多存在一条 active 状态的旅程。购买多疗程产生多条旅程时，后续旅程停留在 pending_schedule，待前一条 completed 后才允许排期激活，防止推送叠加。[Assumption, TBD：多疗程是否允许并行见 11]

  • 幂等去重：每条推送任务对应唯一 dedupeKey，调度器重复扫描、多实例并发均不会产生重复通知。
  • 免打扰：21:30 后不发送任何健康助手推送（含升级提醒），到点任务顺延至次日 07:30 合并为一条。[Assumption, TBD：免打扰时段]

05清肠药物双路径

5.1 药物与就绪定义

  • 清肠药物 = 聚乙二醇电解质散（文档指定，2 袋 + 2000mL 水冲服）。平台上架为普通商品，供应商供货，走既有商品/订单/支付/佣金体系，不新增支付逻辑。
  • 就绪（ready）判定：平台购买路径——关联订单已支付且用户点击「已备好」（或订单状态进入 shipped 后用户确认收货）；自购路径——用户提交自购确认即视为就绪。就绪状态冗余存储于旅程的 bowelPrepStatus。
  • 两条路径互斥可切换：未就绪前可任意切换；任一路径达成就绪后锁定，不再展示另一路径入口（保留记录）。

5.2 路径 A：平台购买

健康助手清肠卡→ 「从平台购买」→ 确认商品/收货信息→ 生成销售订单（服务端取价）→ 支付（现有链路）→ 商家发货→ 用户点「已备好」→ 就绪
  • 下单入口固定在健康助手清肠卡与 D-2/D-1 推送的跳转落地页；商品由平台运营配置为「清肠药」专用商品（SKU 标记 bowel_prep 用途），价格、库存、佣金完全复用现有体系，金额单位沿用 *Cents。
  • 生成的订单与正常商城订单同构（SalesOrder + SalesOrderItem），只是在 BowelPrepRecord 中回填 orderId 建立关联；该订单的退款按既有售后规则处理，退款成功会联动清除就绪状态并重新触发提醒（见 8.6）。
  • 为保证时效，下单页提示「建议在移植日前 3 天 24:00 前完成购买」。[Assumption, TBD：物流时效承诺]

5.3 路径 B：用户自购

健康助手清肠卡→ 「我已自行购买」→ 填写药品名（默认聚乙二醇电解质散）+ 购买渠道说明（选填）+ 凭证照片（选填）→ 提交确认 → 立即就绪
  • 自购确认是声明式动作，不做真实性校验；提交后展示清肠操作指引预告，强化「移植前 1 天晚饭后服用」的预期。
  • 商家可查看自购备注与凭证，用于线下跟进核实；商家无权修改用户填写内容，只能在用户授权后代为点击「已备好」。

5.4 就绪状态机与升级提醒

bowelPrepStatus含义迁移条件
none未选择路径/未就绪初始；或平台订单全额退款后回退
platform_ordered平台已下单待确认备好平台订单支付成功
self_confirmed自购已确认（就绪）提交自购确认

D-1 12:00仍未就绪升级推送用户（催办语气）+ 向商家发预警通知（客户姓名/移植日/当前状态/联系方式）
D-1 19:30仍未就绪再次升级推送用户 + 商家预警未消除标记；清肠指引照常发送（指引中前置「若药物未备好请立即联系商家」）
D0 07:30仍未就绪服药提醒照常发送；向商家发送「旅程可能受影响」最终预警

6.3 推送调度实现

// apps/api/src/journeys/journey-dispatch.service.ts
@Cron(CronExpression.EVERY_5_MINUTES)
async dispatch() {
  // 1. 到点任务：status=pending 且 scheduledAt <= now 且 journey.status=active
  // 2. 逐条在事务内：创建 Notification(dedupeKey='jpt:'+taskId) → 任务置 sent
  //    dedupeKey 冲突 = 已发过，直接置 sent（多实例并发安全）
  // 3. 过期处理：scheduledAt < now-2h 的 pending 任务置 skipped(expired)
  // 4. 免打扰：21:30~07:30 窗口内到点任务顺延/合并（merged_quiet_hours）
}
@Cron(CronExpression.EVERY_DAY_AT_1AM)
async rollover() {
  // 阶段推进推导、dayOffset>35 旅程置 completed、D-2/D-1 就绪检查任务动态生成
}
  • 复用现有 @nestjs/schedule（reminders.service 已有同款 Cron 模式），无新增基础设施。
  • 升级提醒（D-2/D-1 检查点）不预生成，由每日 rollover 任务按就绪状态动态判定生成，避免「已就绪却仍收到催办」。
  • 服务器默认 UTC 运行时，scheduledAt 在排期生成任务时即按 Asia/Shanghai 换算为绝对时间存储，调度比较无需时区计算。

6.4 订单系统联动点

  • 开通钩子：sales-orders.service 支付成功事务内，检测订单项商品类目是否为移植服务（新增类目 key transplant_service），是则同事务创建旅程（失败回滚保护：旅程创建失败不阻断支付，改为事务后补偿重试 + 告警）。
  • 取消钩子：订单全额退款完成（refunded）→ 关联旅程置 cancelled，未发任务置 skipped(cancelled)；部分退款不取消旅程。
  • 清肠药订单：由 bowel-prep/platform-order 生成，支付成功后 bowelPrepStatus → platform_ordered；该订单全额退款 → bowelPrepStatus 回退 none 并清除 readyAt，重新纳入提醒。

08异常与边界情况

#场景处理规则
8.1订单支付成功但旅程创建失败（DB 异常等）不阻断支付；事务后补偿任务每 10 分钟重试，连续失败写 SystemAlert 告警平台
8.2支付后用户一直未设置移植日pending_schedule 期间每 2 天晚场发一次排期引导通知（最多 5 次）；商家列表显示「待排期」供线下跟进
8.3移植日改期已发送任务不动；未发送任务按新日期全量重建（templateVersion+1）；dayOffset 已越过的新阶段任务直接置 skipped
8.4暂停（发热 ≥37℃ / 生理期 / 个人原因）暂停时刻起未发任务挂起（skipped(paused)）；恢复时必须重设移植日并重建任务；暂停跨不过清肠就绪逻辑——就绪记录保留
8.5订单全额退款旅程 cancelled，未发任务 skipped(cancelled)，清肠药关联订单若在途一并走售后流程
8.6清肠药平台订单退款bowelPrepStatus 回退 none、清 readyAt；若 dayOffset ≤ -1 重新触发就绪检查与升级提醒
8.7调度器多实例/重复扫描Notification.dedupeKey 唯一约束兜底，重复投递幂等；任务置 sent 与通知创建同事务
8.8任务过期（服务停机、用户长期未打开）超过 2 小时未投递置 skipped(expired) 不补发；停药类关键提醒由次日早场合并提示「昨日提醒已过期，请查看时间线」
8.9用户购买多疗程每商品行一条旅程；已有 active 旅程时新旅程禁止激活，UI 提示「完成当前疗程后可排期」
8.10自购确认后又说没买到就绪后允许用户「撤销就绪」（回到 none），撤销动作记录审计日志；D-1 后撤销会即时触发商家预警
8.11移植日设置为过去日期接口拒绝（transplantDate ≥ 明日）；前端日期选择器同步禁用
8.12跨时区用户本期固定按 Asia/Shanghai 计算与投递，海外用户感知偏差在文案中不做承诺[Assumption, TBD]
8.13账号注销/退款后历史数据旅程与推送记录保留（审计需要），C 端不再展示入口
8.14清肠药商品下架/无库存平台购买入口置灰并提示「暂不可购，请选择自行购买」；自购路径始终可用（保底路径）

10.2 验收标准（可测断言）

  1. AC-01 开通：C 端注册 → 下单含移植服务商品 → 支付成功 → 5 秒内 GET /journeys/mine 返回 1 条 pending_schedule 旅程；重复支付回调仍只有 1 条。
  2. AC-02 排期：设置移植日 = 明日 + dosingScheme=morning_once → 生成任务数 = 覆盖天数 × 3（准备期 7 天 × 3 + 移植期 6 天 × 3 + 恢复期 30 天 × 3 = 129）；时间线接口按 dayOffset 过滤正确。
  3. AC-03 推送时点：mock 服务器时间至 D0 07:31 → 用户收到早场服药提醒，正文含「晨起空腹」「10 粒」「≤37℃ 温凉水」；dosingScheme=twice_daily 时晚场含第二次服药提醒，morning_once 时晚场不含。
  4. AC-04 内容映射：D-1 晚场正文含「2 袋」「2000mL」「少量多次」「无渣清水状」「当晚不可再进食」「空腹 8~10 小时」；准备期中场含「抗生素」「20mg」禁忌要点。
  5. AC-05 幂等：双开 API 实例运行调度器 30 分钟，Notification 表中 jpt:* 无重复 dedupeKey。
  6. AC-06 过期与免打扰：停机 3 小时后恢复，过期任务全部 skipped(expired) 且无补发；21:35 到点任务合并至次日 07:30 一条。
  7. AC-07 平台购买路径：健康助手发起 platform-order → 生成订单（金额为服务端取价）→ 支付 → bowelPrepStatus=platform_ordered → 点「已备好」→ ready 且 readyBy=customer。
  8. AC-08 自购路径：提交 self-confirm → bowelPrepStatus=self_confirmed；商家端可见备注，不可编辑。
  9. AC-09 升级提醒：D-1 12:00 未就绪 → 用户收到催办推送且商家收到预警通知；就绪后预警消除；D0 仍未就绪 → 商家收到最终预警。
  10. AC-10 取消与退款：订单全额退款 → 旅程 cancelled、未发任务 skipped、不再收到任何推送；清肠药订单退款 → 就绪回退 none。
  11. AC-11 权限：customer 访问他人旅程 403；merchant 访问非名下旅程 403；platform 全量可查。
  12. AC-12 回归：pnpm -r typecheck、pnpm build、e2e-flow.py 69 断言、finance-probe.py 25 断言全部通过。
