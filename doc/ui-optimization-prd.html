小程序与后台管理系统 UI 界面优化 PRD

版本：v1.0（待评审） 日期：2026-10-24 涉及端：apps/admin、apps/mini-b、apps/mini-c 关联文档：doc/mall-distribution-prd.html

1. 背景与目标

1.1 背景与问题

商城分销系统已完成核心业务闭环（商品、订单、盒码渠道、佣金、对账、结清），三端 UI 已分别基于 antd 5 + ProComponents（admin）与 NutUI React Taro 4.0.0-beta.9（mini-b / mini-c）搭建。当前存在以下已确认问题：

端已确认问题影响
三端共性 无主品牌色与统一设计令牌；admin 使用 antd 默认主题，小程序仅靠零散 CSS 变量覆盖 三端视觉割裂，新增页面样式靠复制，无法统一演进
admin 金融类操作（登记支付、票证登记、结清、调整）弹窗交互不统一，部分缺二次确认与操作结果反馈 资金相关误操作风险高（资金安全审计已收敛后端校验，前端确认层未统一）
admin 列表页 API 直接返回全量数组、前端无分页/虚拟滚动策略 订单、佣金流水等数据量增长后存在渲染性能隐患
admin 金额 / 费率格式化在各页面调用时机不统一（formatCents） 存在展示口径不一致风险
mini-b / mini-c NutUI beta.9 Input 组件输入过程不触发 onChange（仅 onBlur 派发），现以 value + onBlur 变通 受控输入无法实时校验，体验受损（依赖官方正式版修复，见 §6）
mini-b / mini-c Toast.show 依赖页面挂载 <Toast id>，漏挂页面反馈静默丢失 用户操作无反馈，疑似 bug
mini-c 解读报告未复核（contentHidden）状态仅纯文案提示；订单状态无可视化 C 端用户不理解「解读尚未发布」的等待语义

1.2 优化目标（可观察结果）

  • 三端颜色、字号、间距、圆角由同一份设计令牌定义，新增页面不引入令牌之外的色值与字号。
  • 平台运营在 admin 执行任何资金类写操作前，看到操作对象、金额与后果说明，并必须显式确认；操作成功后看到结果摘要。
  • C 端用户从首页到支付完成的路径中，每个页面有明确主行动按钮与价格展示；解读未发布时看到明确的等待态说明。
  • 商家在 mini-b 首页可一眼看到当日关键经营指标。
  • 所有操作反馈（成功 / 失败 / 加载）在三端以统一组件呈现，不存在静默失败。

4. 功能需求

FR-DS 设计令牌与三端主题 P0

目的

建立三端统一的视觉语言，消除逐页面手写色值 / 字号的做法。

处理规则

  • 令牌分层：基础令牌（色板、字号阶梯、4px 基数间距阶梯、圆角）→ 语义令牌（主色、成功 / 警告 / 错误、文本一级 / 二级、边框、背景）。
  • admin：语义令牌映射到 antd theme token；禁止组件内联 style 中出现令牌外色值（图表等特例除外）。
  • 小程序：语义令牌映射到 NutUI CSS 变量（变量名以 NutUI dist 样式表实际定义为准）+ 全局样式文件；单个页面不得覆写语义色。
  • 设计稿（Figma）与代码令牌同名，一一对应。

结果与状态

三端核心页面切换为新主题后，走查清单中不存在令牌外色值 / 字号；后续新增页面默认继承主题。

示例：语义令牌（示意色值，最终以设计稿冻结版本为准 [TBD]）

colorSuccess 成功
colorWarning 警告

FR-A1 admin 布局与导航重组 P1

目的

21 个页面按业务域分组，缩短平台运营定位目标页面的路径。

处理规则

  • 侧边菜单按业务域分组：商品 / 订单 / 渠道（商家、销售、盒码）/ 资金（对账单、结清、票证）/ 系统（用户、设置）。具体分组命名以设计稿为准 [TBD]。
  • 菜单导航沿用 ProLayout 官方规范模式（menuItemRender + Link），禁止自定义 <a onClick> 跳转（已知静默失效问题）。
  • 页面框架统一 PageContainer + 面包屑；列表页默认 ProTable，表单弹窗默认 ModalForm。

异常

无权限菜单不渲染（沿用现有 @Roles 对应的前端路由过滤）；直接访问无权限 URL 时显示 403 空态页（复用 FR-X 组件）。

FR-A2 admin 金融操作链路：确认与结果反馈 P0

目的

资金类写操作（登记支付、票证登记、对账调整、结清 / 重开）在前端形成统一的「确认 → 执行 → 结果摘要」闭环，防止误操作。

触发

平台运营角色在对账单详情、订单详情等页面点击对应操作按钮。

处理规则

  • 所有资金类操作弹窗采用统一结构：操作对象摘要（单号 / 周期）→ 关键金额（表格化展示，金额展示遵循 §5.1）→ 后果说明（如「结清后不可撤销，需重开才能调整」）→ 确认按钮。
  • 登记支付固定按订单应付全额登记（不提供金额输入），与后端「支付金额必须等于订单应付」校验口径一致。此为 2026-10-24 金融安全审计已收紧落地的既有行为，本次仅统一弹窗结构与结果反馈规范，不改登记逻辑。
  • 确认按钮文案写明动作（如「确认结清」），危险操作（结清、重开、调整冲回）使用主色 + 二次确认，不用红色误导师文化歧义——红色仅用于错误反馈。
  • 执行中按钮 loading 且防重复提交；后端返回成功后展示结果摘要（本次变动金额、变动后状态），失败时展示后端错误文案并保留弹窗内容不清空。

权限

与后端一致：对账类操作仅平台角色可见可操作；其他角色不渲染入口。

异常

  • 应付为 0 且无票证：结清按钮禁用并说明原因（对应后端 D5 规则）。
  • 提交时网络失败 / 超时：保留弹窗与已填内容，允许重试；不自动重复提交。
  • 状态已被他人变更（如已结清）：以后端错误提示为准刷新页面状态。

FR-A3 admin 高频列表页性能与批量操作 P1

目的

订单、佣金流水、对账单等列表在数据量增长后保持可用；高频批量动作减少重复进出详情页。

处理规则

  • 在 API 分页改造完成前（见 §6），列表页统一采用前端分页 + 大数据量时开启虚拟滚动；单页渲染行数设上限 [Assumption, TBD：默认 200 行]。超出上限时不截断数据（虚拟滚动仍渲染全部），仅在列表顶部显示警告条：「数据量超过 200 条，建议使用筛选条件缩小范围」，避免用户误以为数据丢失。
  • 列表支持列宽调整与列显示记忆（localStorage 按页面 key 存储）。
  • 批量操作工具栏在勾选行后出现，仅暴露当前状态下合法的批量动作；批量动作遵循 FR-A2 的确认与结果反馈规范。
  • 筛选项与列表刷新遵循 ProTable 默认交互；刷新后保留筛选与分页。

异常

空结果显示统一空态（FR-X）；接口失败显示错误态并提供重试按钮。

FR-C1 mini-c 下单链路视觉与交互升级 P1

目的

首页 → 商品详情 → 确认订单 → 支付结果四个页面形成清晰转化路径，每页有唯一主行动按钮。

核心流程

首页浏览→ 商品详情→ 确认订单→ 支付结果→ 查看订单 / 解读进度

处理规则

  • 价格展示遵循 §5.1 金额规范，主价格使用主色 + 大号字，单位「¥」与金额同基线。
  • 主行动按钮（立即购买 / 提交订单 / 完成）固定在底部安全区上方，宽度通栏。
  • 确认订单页展示渠道归属信息（若有 channelCode / 盒码归属）的只读摘要，不改变现有归属判定逻辑。
  • 支付结果页区分成功 / 失败 / 处理中三态；失败态提供「重新支付」与「查看订单」两个出口。
  • 输入类交互维持现有 value + onBlur 变通方案，待 NutUI 正式版升级后回滚（见 §6）。

异常

商品已下架 / 库存不足：详情页主按钮置灰并说明；下单接口返回业务错误时以统一 Toast（§5.2）提示并返回上一页保留选择。

FR-C2 mini-c 解读报告与订单状态可视化 P2

处理规则

  • 解读报告未发布（contentHidden）时，页面展示明确的等待态：说明「解读尚未发布」、预期等待语义与咨询入口 [TBD：是否展示预计发布时间需业务确认]。
  • 订单详情增加状态步骤条，节点与现有订单状态机一致（待支付 → 已支付 → 履约中 → 已完成 / 已退款），当前节点高亮；退款 / 售后状态以分支标签呈现，不挤占主步骤条。步骤条节点命名与代码状态枚举（OrderStatus）一一映射，以代码枚举为准，设计稿不得自造状态名。

FR-B1 mini-b 经营看板与商品管理 P2

处理规则

  • 首页看板以卡片呈现关键指标（今日订单、今日收入、待处理事项），指标金额遵循 §5.1；数据为现有接口聚合，不新增统计口径 [Assumption, TBD：指标清单需与商家角色确认]。「待处理事项」暂无明确口径与数据来源 [TBD：需确认是否存在待发货 / 待审核等业务态，若现有接口无法支撑则替换为「本月累计收入」等已有指标]。
  • 商品 / 盒码列表支持滑动操作（编辑 / 上下架）与批量选择；批量操作遵循 §5.3 确认规范。
  • 表单页维持现有组件与 onBlur 变通，仅做布局与视觉对齐。

FR-X 三端空态 / 异常态 / 反馈统一 P3

处理规则

  • 建立三端各自的统一组件：空态（Empty）、页面级错误态（含重试）、加载骨架屏；各页面不得自行实现一次性空态。
  • 小程序端全局封装 Toast 调用，页面无需手动挂载 <Toast id>（封装层保证挂载），消灭反馈静默丢失。
  • token 失效 / 账号不存在（如 seed 重跑后旧 token）：统一跳转登录页并提示重新登录，不留白屏。

5. 共享规则

5.1 金额与费率展示

  • 所有金额以后端「分（*Cents）」字段为准，展示层统一经 formatCents（@mall/shared）格式化；禁止页面内自行除以 100 或拼接。
  • 费率字段（*Bps）展示为百分比，保留规则与现有页面一致；表格金额列右对齐、等宽数字。

5.2 反馈规范

  • 操作成功：轻提示（Toast / message）；涉及资金或状态不可逆变更的操作：结果摘要（FR-A2）。
  • 操作失败：展示后端返回的错误文案，不包装、不吞错；表单类失败保留用户已填内容。
  • 加载超过 300ms 显示加载态；按钮提交期间防重复点击。

5.3 确认规范

  • 资金类、状态不可逆、批量影响勾选行数 ≥ 2 的操作，必须二次确认，确认弹窗包含操作对象与后果说明。计数口径按用户勾选行数判定；单条详情内的操作无论涉及多少子明细（如对账单内多条佣金）均视为单行操作，按其自身性质判断是否需确认。
  • 普通可逆操作（编辑、筛选）不弹确认，避免确认疲劳。

5.4 权限

  • 前端入口显隐与后端 @Roles 保持一致：无权限即不渲染入口，直接访问路由显示 403 空态。
  • 前端显隐仅为体验优化，不替代后端鉴权。
